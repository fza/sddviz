The desktop application links against the macOS 26 software development kit, and its window declines
the full-screen mode.

macOS decides how it draws a window's own close, minimise and zoom controls from the kit a binary
links against. A binary linked against the version 14 kit gets the older, smaller controls whatever
its window options say. The environment supplied that kit, so no window setting could reach the
appearance. `apple-sdk_26` is now pinned beside the other packages, and the desktop scripts point
`SDKROOT` and the two compiler variables at it. The deployment target stays at version 14.

Measured in a running window, the controls move from twelve by fourteen points to sixteen by
sixteen, which is the flat pair the current system draws.

## The window keeps its own space

The window refuses the full-screen mode, so its zoom control grows the window to the screen it sits
on and leaves it a window. A reader keeps every other window beside this one. Measured, the window
reaches the full screen below the menu bar and reports itself as not full screen.

Its title bar hides and insets, and its drag region matches the bar the page draws. The system's
controls then sit eighteen to thirty-four points down. The page's own bar is twice that centre tall,
so centring its contents puts them on the same line.

## What it costs

Three build scripts now carry four exported lines each, and a reader changing one has to change
three. The pin names a version, so moving to a later system's controls takes a deliberate edit
rather than following the machine.

Setting a developer directory alongside the kit loses: it breaks the tool that resolves a kit path
and fails the build. Reaching for the system's own kit outside the environment loses too. The build
would then depend on what a machine happens to carry, rather than on what the environment pins.

Nothing follows from this on its own, which is what makes it terminal at capture.

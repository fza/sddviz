Searching a graph runs in sdd, and the viewer supplies the provider the repository names.

`Search(phrase)` reports the entries sdd matched, in the order sdd ranked them, beside the mode that
produced them. Comparing an entry against a phrase never happens here. A request names an explicit
limit, because sdd answers with ten where a request names none, which fills a table too thinly to
read a graph by.

## The word count decides the mode

One word is what a reader types to find a token they already know. Matching it literally beats the
nearest neighbours of its meaning, so a single word searches over terms. Several words describe a
thing rather than name it, which is what a vector space answers well, so they reach the vector search
wherever one answers.

Whether one answers comes from sdd's own `Info`. It reports `vector,text` where the mount carries
both an embedding provider and a stored index, and `text` alone otherwise.

## Where the provider and the index come from

The repository names its own embedding provider. `.sdd/config.local.yaml` overlays `.sdd/config.yaml`
field by field, which is where a machine keeps the endpoint and the key no checkout shares.

The viewer speaks one transport, the `POST {endpoint}/v1/embeddings` contract that OpenAI and its
compatible self-hosted services answer. A repository naming any other provider searches over terms,
which is an answer rather than a failure.

The stored index sits in the machine's cache under `$XDG_CACHE_HOME/sdd`, keyed by the repository
identity and by a fingerprint of the embedder. That is the layout sdd's own tool fills. Reproducing
the fingerprint exactly is what lets the viewer read the index that tool already built. Computing it
differently builds a second index beside it and embeds every entry again to fill one, so a test holds
the fingerprint to the string sdd derives.

**Read-only holds.** The cache is not the repository the viewer reads. sdd reconciles the
index before each vector search, embedding whatever is missing and writing it to that cache, and
leaves an index already current alone.

## Filtering by topic

Choosing topics narrows the listed entries to those carrying every one chosen, because choosing an
area and a facet together asks for the overlap. This happens in the front end over the records
already in hand. sdd's search filters by type, layer, and kind, and carries no topic filter.

A search outlives a switch between the views, and so does a topic choice.

## What it costs

A viewer opening a graph no tool has indexed embeds every entry on its first search of several
words. Against a paid endpoint that spends money the reader did not ask to spend. Keeping the index
in memory instead loses: it ignores what the tool already built and pays the wait again on every
launch. Refusing to write at all loses too, since a graph captured since its last indexing would
silently fall back to terms.

A repository naming `ollama` gets term search, though sdd itself speaks that transport.

Nothing follows from this on its own, which is what makes it terminal at capture.

A reader reaches a graph three ways, and only one of them does the work.

`OpenRepository(path)` takes the path of a checkout carrying `.sdd/config.yaml`, reads `graph_dir`
from it, and opens the store over that directory. Every build answers it.
`ChooseRepositoryDirectory()` opens the native folder picker and returns the chosen path, which the
front end then passes to the first. Desktop builds alone answer it. The first command-line argument
names a repository to open at once, and `Startup()` reports what opened or why it did not.

The split exists because a server build carries no native dialogs. Keeping the work in a method that
takes a path lets every build reuse it, while the picker stays one call a server build never makes.
The command-line argument is what gives such a build a way in at all.

A single argument-less method that opens the picker itself loses. It needs the least front end code
and reads as the most obvious desktop behaviour, and it would have to exist twice, once per build,
for one job.

A configured list of repositories with no picker loses as well. It behaves identically in both builds
and suits a server holding a fixed set of clones. It offers no discovery, and a reader at a desktop
expects to point at a folder.

The accepted cost is three entry points where one would look simpler, and a front end that wires them
together.

Nothing follows from this on its own. It constrains work other entries commission.
